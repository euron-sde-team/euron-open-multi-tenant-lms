# ADR 0004: Storefront pages are JSON section lists

## Status

Accepted.

## Context

Every tenant needs a storefront that looks like their brand: a home page, course and book
landing pages, about, contact, legal pages. Tenant staff are not developers. The platform
must render hundreds of storefronts from one deployment, keep them fast, keep them safe for
learners, and keep improving the building blocks without breaking existing pages.

The options were a page builder that stores HTML, per-tenant code (themes as code
packages), or structured data rendered by shared components.

## Decision

- A page is a row in `tenant_pages`: `sections` (an ordered list of `{ type, variant,
  content, settings, visible }`), `theme` (colours for light and dark, fonts, spacing, radii)
  and `seo`. Header, footer and navigation are `tenants.layout`.
- Section types are a closed set defined in `packages/shared` (types and Zod schemas) and
  `packages/ui-config` (registry and default content), rendered by components in
  `packages/core`. The tenant admin and the storefront use the same components, so the
  editor preview is the storefront.
- Page templates in `packages/lms-templates` are section lists plus a theme preset. Applying
  one copies it into the tenant's page; later edits to the template do not touch it.
- The storefront applies the theme in two layers: critical CSS variables rendered on the
  server for the first paint, then `TenantThemeProvider` on the client.
- Tenant-written HTML is allowed only as a separate render mode (`CUSTOM_CODE`), shown in a
  sandboxed iframe without `allow-same-origin`, never mixed into the section tree.

Details: [templates-and-theming.md](../architecture/templates-and-theming.md).

## Consequences

Positive:

- A component fix or improvement reaches every tenant's pages on the next deploy.
- Pages are data: they can be validated, versioned, generated by AI authoring
  ([ai-authoring.md](../architecture/ai-authoring.md)), copied between tenants and
  migrated.
- Custom-code pages run in an opaque origin, so their scripts cannot reach the learner's
  token. (Some components still render tenant-supplied HTML fields directly; see
  [security.md](../architecture/security.md#known-gaps).)
- One theme per site (the homepage's) keeps the storefront consistent.

Trade-offs:

- Tenants can only build what the section set allows. A new layout means a new section type
  or variant in the shared packages and a release.
- Section content shapes are long-lived contracts: renaming a field breaks stored pages
  unless the component reads both shapes.
- Adding a section touches several files in three packages and two apps
  ([add-a-template.md](../guides/add-a-template.md)).
- Theme values are strings rendered into CSS, so the storefront writes only values that pass
  `safeCssValue` (plain colours, lengths, numbers, font lists); anything else falls back to
  the default ([security.md](../architecture/security.md#6-web-and-transport)).

## Alternatives considered

- **Stored HTML from a WYSIWYG builder.** Flexible, but every page becomes an XSS review and
  no improvement ever reaches existing pages.
- **Per-tenant theme packages.** Real code per tenant means per-tenant builds and per-tenant
  bugs.
- **A headless CMS.** Another system to run and another tenant model to map.
